# Lab Guide — Safe Testing Targets

osint-recon is for authorized assessments. The safest way to learn and test
it is against documentation domains and infrastructure you own.

## 1. IANA documentation domains

`example.com`, `example.org` and `example.net` are reserved by RFC 2606 for
documentation. They are the canonical smoke-test targets:

```sh
osint-recon dns example.com
osint-recon tech example.com
osint-recon subdomain example.com
osint-recon asn example.com
osint-recon ct example.com
osint-recon ghdork example.com
osint-recon email example.com
osint-recon metadata example.com
osint-recon full example.com --json output/example.json
```

Expected: DNS records resolve (A/AAAA/MX/NS/TXT), tech fingerprint shows a
minimal stack, and the email/metadata modules return empty results — empty
output from a source with nothing to give is a *successful* graceful run,
not a failure.

## 2. Your own infrastructure

The most realistic lab is a domain you own:

1. Register a cheap domain or use a subdomain of one you control.
2. Publish a small static site with a `contact` page listing a test address
   and a linked PDF generated by a known tool (so Author/Creator metadata
   is predictable).
3. Issue a certificate (Let's Encrypt) so the domain appears in CT logs.
4. Run `osint-recon full yourdomain.tld` and compare output against ground
   truth you planted.

This validates every module end-to-end with zero third-party impact.

## 3. Intentionally-vulnerable / practice environments

Public practice targets designed for security training (e.g. local
OWASP Juice Shop instances) are suitable for the `tech` module. Check each
environment's terms before pointing anything at hosted instances.

## What NOT to do

- Do not run against third-party domains you are not authorized to assess.
- Do not raise `--rate` to "see what happens" — the politeness limit is a
  design constraint, not a suggestion.
- Do not treat this tool as a scanner: there is deliberately no port
  scanning, brute forcing, or probing of non-public paths.

## Verifying exports

```sh
osint-recon dns example.com --json output/dns.json --csv output/dns.csv
```

- `output/dns.json` — full structured payload (`module`, `domain`, `records`, `errors`).
- `output/dns.csv` — flat `Type,Record` rows for spreadsheets/reporting.

With `full`, CSV export is skipped by design (one flat table per module);
use `--json` for the combined bundle.
